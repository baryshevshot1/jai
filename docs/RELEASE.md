# Ритуал выпуска

Что прогнать, в каком порядке, что проверить руками и что приложить к сборке.
Документ существует потому, что **GitHub Actions этому проекту недоступны** — аккаунт
заблокирован по оплате. Красный и зелёный свет мы даём себе сами, и от этого гейт
должен быть строже, а не мягче: то, что обычно делает CI, здесь делают скрипты в
репозитории и этот список.

---

## 1. Ярусы проверок

| Ярус | Когда | Команда | Бюджет |
|---|---|---|---|
| Быстрый | каждый коммит (хук `pre-commit`) | `tools/check.sh --fast` | секунды |
| Обычный | по ходу работы | `tools/check.sh` | 1–2 минуты |
| Полный | каждый push (хук `pre-push`) | `tools/check.sh --full` | минуты |
| Релизный | перед сборкой клиенту | `tools/check.sh --release` | десятки минут |

Что добавляет каждый следующий ярус:

- **обычный** — clippy без предупреждений, сборка фронтенда, сверка разметки и
  контракта команд (`tools/check-dom.py`);
- **полный** — матрица фич (`--no-default-features`, `--all-features`), сборка и
  тесты под Linux в Docker, кросс-проверка Windows;
- **релизный** — аудит зависимостей и smoke-тест собранного бандла
  (`tools/smoke.sh` → `jai --self-check`).

### Хуки

Живут в репозитории (`.githooks/`) и включаются одной строкой:

```bash
git config core.hooksPath .githooks
```

`pre-commit` — быстрый ярус, `pre-push` — полный и блокирующий.
**`--no-verify` считается инцидентом:** значит, в репозиторий уехало непроверенное,
и об этом надо сказать вслух, а не молча.

### Зелёный штамп

Полный и релизный ярусы при успехе пишут `.check/last-green.json`: коммит, ветка,
ярус, версии `rustc`/`node`/ОС, перечень выполненных проверок.

Штамп **не выдаётся**, если хоть одна проверка была пропущена (нет `cargo-xwin`, не
запущен Docker и т. п.). «Проверено, кроме Windows» и «проверено» — разные вещи, и
различать их должен файл, а не память.

`.check/` в `.gitignore`: штамп — локальный факт этой машины. Чужой штамп означал бы
«проверено» там, где ничего не проверялось.

## 2. Сборка выпуска

```bash
tools/check.sh --release      # обязательно: без штампа сборка не пойдёт
tools/release.sh --check      # сухая проверка готовности
tools/release.sh              # собственно сборка
```

`tools/release.sh` **отказывается** собирать, если:

- штампа нет вовсе;
- штамп относится к другому коммиту;
- штамп выдан не релизным ярусом (`fast`/`normal`/`full`) — аудит зависимостей
  входит только в `--release`, а автоматических проверок больше нет вовсе;
- в рабочем дереве есть несохранённые изменения.

Все четыре отказа проверены экспериментом, а не предположением.

Рядом с бандлом кладётся `build-report.json`: коммит, ветка, время и машина сборки,
ярус гейта, версии инструментов и **список известных дыр**. Для коробочного продукта
это ещё и документ поставки — иначе «что именно стоит у клиента» потом не восстановить.

## 3. Известные дыры в приёмке

Записаны здесь намеренно: дыра, о которой знают и молчат, ничем не отличается от
дыры, о которой не знают.

### 3.1. Windows не запускался ни разу

**Уровень 1 (есть и работает):** `cargo check --target x86_64-pc-windows-msvc` через
`cargo-xwin` в полном ярусе. Ловит непортируемые пути, разделители и ветки
`#[cfg(windows)]` — детект видеопамяти через DXGI, управление процессом движка, — которые
на Mac не компилируются вовсе и потому не проверялись никогда.
**О работе программы не говорит ничего.**

Что для этого нужно на машине разработчика (гейт проверяет сам и называет недостающее):

```bash
cargo install cargo-xwin --locked
rustup target add x86_64-pc-windows-msvc
rustup component add llvm-tools        # даёт llvm-ar (он же llvm-lib) и lld-link
brew install llvm                      # ради llvm-rc — компилятора ресурсов Windows
```

`llvm-lib` — это тот же `llvm-ar`: он смотрит на имя, под которым его позвали, поэтому
`check.sh` кладёт симлинк в `.check/win-tools` сам. `llvm-rc` в rustup нет, он только в
полном LLVM. Пока хоть одного инструмента нет — шаг **объявляется пропущенным и зелёный
штамп не выдаётся**.

Ограничение внутри ограничения: кросс-проверка идёт с `--no-default-features`, потому
что `whisper-rs` собирает C++ через cmake и тулчейном xwin не проходит. Значит,
**модуль голосового ввода под Windows не проверен даже компиляцией.**

**Уровень 2 (нет):** собрать установщик и запустить его на живой Windows. Стенда нет.
До появления стенда выпуск под Windows — это выпуск непроверенного.

Что понадобится, когда стенд появится: установщик ставится офлайн (WebView2 уже
`offlineInstaller`), приложение стартует, кнопка микрофона работает, модель ставится
с флешки, пути данных совпадают с ожидаемыми (`--self-check`).

### 3.2. Голос под Linux не проверяется в контейнере

`whisper.cpp` не собирается на ARM64 Linux (контейнер на Apple Silicon): системный
GCC не включает fp16-инструкции. Поэтому Linux-ярус идёт с `--no-default-features`.
Целевая платформа — **x86_64** Linux, там сборка штатная, но в нашем контуре она не
проверяется. Исключение не должно расползаться на остальной Linux-код.

### 3.3. Что не проверяет ни один автоматический тест

- **Качество распознавания русской речи.** Модель `ggml-small.bin` (465 МБ) выбрана
  как компромисс «точность / размер флешки». Если качество окажется недостаточным,
  следующая ступень — `medium` (~1.5 ГБ), втрое тяжелее для носителя.
- **Работа с реальной флешки** на машине клиента.
- **Поведение на 6 ГБ видеопамяти** (целевой Linux-ПК).
- **Что окно вообще нарисовалось.** `--self-check` доходит до путей и команд, но
  webview не поднимает. Это закрывается только глазами — раздел 4.

## 4. Чек-лист ручной проверки

Прогонять на собранном бандле (`.app` / установщик), **не** в `tauri dev`.

**Старт**

- [ ] Приложение открывается по иконке, окно рисуется целиком.
- [ ] Плашки об отказе старта нет. Если есть — читать список модулей на ней.
- [ ] Настройки → «Проверка системы» → «Технические сведения»: версия и коммит
      совпадают с тем, что собирали; «Возможности» содержат `voice`.

**Голосовой ввод**

- [ ] Карточка «Голосовой ввод» видна в настройках.
- [ ] Модель не установлена → кнопки микрофона нет (а не мёртвая кнопка).
- [ ] «С флешки/диска…» находит носитель и ставит модель; при вынутой флешке —
      понятный отказ, а не «error».
- [ ] «Установить» качает модель; в подписи видны проценты, скорость и остаток.
- [ ] **Обрыв связи** посреди загрузки (выдернуть Wi-Fi на 10 секунд): загрузка
      продолжается сама, прогресс не откатывается на ноль.
- [ ] «Отмена» посреди загрузки → карточка показывает «скачано N из M» и предлагает
      «Продолжить»; после нажатия загрузка идёт дальше, а не с начала.
- [ ] «Начать заново» выбрасывает недокачанное и начинает с нуля.
- [ ] После установки появляется кнопка микрофона — **без перезапуска приложения**.
- [ ] Зажать микрофон, сказать фразу, отпустить: «Говорите…» → «Распознаю…» → текст
      дописывается к уже набранному, не затирая его.
- [ ] Отпустить кнопку, уведя курсор далеко в сторону — запись не залипает.
- [ ] Alt+Tab во время записи — микрофон закрывается, сказанное распознаётся.
- [ ] **Escape** во время записи — микрофон закрывается, в поле НИЧЕГО не дописывается.
- [ ] Очень короткое нажатие («тык») — понятная подсказка, а не ошибка.

**Не сломано ли прежнее**

- [ ] Чат отвечает, стриминг идёт, «Стоп» работает.
- [ ] Документ прикрепляется и индексируется.
- [ ] Онлайн-режим выключен по умолчанию.
- [ ] Модели видны, светофор железа показывает уровень.

## 5. Офлайн-поставка (флешка)

Решение владельца (ADR): **флешка — основной путь, интернет — запасной.** У клиента
интернета нет, и полагаться на скачивание 465 МБ при установке нельзя.

```bash
tools/make-usb.sh --out /Volumes/JAI --installers --models "qwen3.5:9b bge-m3" --voice
```

Ссылка, размер и sha256 модели распознавания заданы **дважды** — в `src-tauri/src/voice.rs`
и в `tools/make-usb.sh`. Разъедутся — флешка соберётся с файлом, который приложение
отвергнет уже у клиента. Их совпадение проверяет тест
`voice::tests::usb_builder_and_app_agree_on_the_model`; правя одно место, прогоняйте
`cargo test`.

## 6. Когда GitHub Actions заработают

Workflow-файлы переведены на `workflow_dispatch` и продолжают документировать, что
должно проверяться. Возврат — по одной строке в каждом:

- `ci.yml` → `on: { pull_request:, push: { branches: [main] } }`
- `release.yml` → `on: { push: { tags: ['app-v*'] } }`
- `audit.yml` → вернуть `schedule:`

Набор проверок в `ci.yml` обязан совпадать с `tools/check.sh`. Источник правды —
скрипт; YAML — тонкая обёртка над ним.
