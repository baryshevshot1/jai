# Кандидаты в ADR — решения, требующие отдельного обсуждения

Заводится в ходе аудита Фазы 0. Это не находки-дефекты, а решения, которые надо принять явно и записать: каждое меняет правила для всего кода, а не одно место.

---

## ADR-К1 — Правило «отказ ≠ пустота и ≠ успех» + механическая проверка

**Проблема.** Аудит A1/A2a обследовал ~336 мест обработки отказов в Rust и 85 вызовов IPC на фронте. 34 места превращают отказ в ложную пустоту или ложный успех, из них 3 уровня P0 (тихая потеря/неудаление данных клиента) — при том что ~296 мест обработаны корректно. Это не разница в аккуратности, а отсутствие сформулированного правила: одни и те же операции в соседних файлах обработаны противоположно (delete_project отказывается удалять при неудачной чистке со ссылкой на «удалил — значит удалено», projects.rs:125-141; каскадное удаление чатов того же проекта глотает пять отказов подряд, projects.rs:145-155).

**Предлагаемое правило (формулировка для CLAUDE.md):**

> Отказ операции над пользовательскими данными нельзя превращать ни в пустоту, ни в успех.
> 1. **Чтение**: «не удалось прочитать» ≠ «пусто». Отказ read/read_dir/parse — это `Err` с человеческим текстом, а не пустой список и не значение по умолчанию. Исключение — `NotFound`, когда отсутствие данных штатно (первый запуск): его отделять явно.
> 2. **Запись**: не строить новое содержимое файла из данных, прочитать которые не удалось (read-modify-write поверх неудавшегося чтения = уничтожение).
> 3. **Удаление**: «удалил» — значит удалено. Не удалилось хоть что-то — операция отказала, с числом и причиной.
> 4. **Best-effort допустим**, но помечается: `// best-effort: <почему отказ здесь безвреден>`. Без пометки — дефект.
> 5. Любое проглатывание, оставляющее пользователя без информации, обязано хотя бы попасть в журнал (`journal::warn/error`) — иначе поддержка слепа.

**Образцы в коде (на них ссылаться при ревью):** `projects.rs:125-141` (отказ удаления вместо ложного успеха, с обоснованием 152-ФЗ); `projects.rs:42-77` (load_projects возвращает Err с текстом «Проекты НЕ потеряны — файл на месте…» именно для показа человеку); `error.rs:73-77` (From<String> честно ставит код unknown, а не угадывает); `journal.rs:163-166` (единственное осознанное глотание — ошибки записи самого журнала, с объяснением).

**Механическая проверка — спроектирована и посчитана.** Запрет «в лоб» невозможен: в проде 69 `let _ =`, 73 `unwrap_or`, 46 `unwrap_or_else`, 30 `if let Ok`, 22 `.ok()` — законных мест кратно больше дефектных. Проверены четыре признака-разделителя:

| Признак | Годится? | Числа |
|---|---|---|
| **Тип операции** (изменяющие `fs::`) | **да, единственный надёжный** | сужает `let _ =` с 69 до **17** — отсекает 75% шума одним фильтром |
| **Граница `#[cfg(test)]`** | **обязательна** | без неё 17 превращаются в 61 (44 хвоста уборки временных каталогов в тестах) |
| Соседний `journal::` | нет | среди 17 файловых мест рядом нет ни одного вызова журнала: законные не логируют по замыслу, дефектные — по недосмотру. Не разделяет |
| Имя переменной (`tmp`, `part`, `probe`) | ловушка | покрыло бы 10 из 15 законных, но пропустило бы ровно дефектные (`provision.rs:544`, `voice.rs:167`) |

**Предлагаемая проверка** (по образцу `tools/check-dom.py` — python, в ярус `--fast`):

```
для каждого .rs в src-tauri/src:
    отрезать хвост от первого «#[cfg(test)]»
    искать:  let _ = (std::)?fs::(remove_file|remove_dir_all|rename|write|copy)
             let _ = write_atomic
             \.ok\(\) на тех же операциях
    пропускать строки, где на этой или предыдущей строке есть маркер:
             // best-effort: <причина>
    падать со списком «файл:строка + фрагмент» и текстом:
             «Отказ файловой операции проглочен без объяснения.
              Либо вернуть Err, либо пометить: // best-effort: почему это безопасно»
```

**Стоимость и сигнал (посчитано на текущем коде):** 17 срабатываний → **3 настоящих дефекта** (`history.rs:153` очистка истории, `projects.rs:155` каскад удаления, `agent.rs:348` журнал 152-ФЗ — то есть ровно найденные аудитом P0/P1) и **14 мест под маркер** (уборка `.part`/`.copy-part`, пробные файлы, ротация журнала, восстановление БД). Разметка — работа на час; после неё проверка ловит новые случаи с нулевым шумом.

**Чего проверка не ловит** (и это надо принять сознательно): `if let Ok(...)` без `else` — регуляркой не берётся, нужен подсчёт скобок; чтение, превращённое в пустоту (`read_settings`, `list_conversations`) — там нет ключевого паттерна, только структура. Эти случаи остаются на ревью и на юнит-тесты «битый файл → не пусто, а ошибка».

**Альтернатива clippy** оценена и отклоняется как первый шаг: `unwrap_used`/`expect_used` дали бы 173 и 21 сработку (почти всё — в тестах, где они уместны), `let_underscore_must_use` — только на `#[must_use]`-типах, то есть мимо `fs::remove_file`. Узкая своя проверка точнее и дешевле.

**Решение принимает владелец.** Цена: час разметки + правки по списку находок; выгода: класс дефектов, давший 3 из 6 P0 аудита, перестаёт возникать незаметно.

## ADR-К2 — Локальный путь производства Windows-сборки

**Проблема.** Установщики под Windows и Linux собирал только GitHub Actions по тегу `app-v*`; после блокировки биллинга (03.08.2026) способа получить `.exe` не осталось вовсе, а Tauri не кросс-компилирует. Это не «CI временно недоступен», а утрата единственного канала производства для приоритетной платформы.

**Что решать:** восстанавливать оплату Actions (быстро, но канал остаётся внешним и повторно ломается) либо завести собственный воспроизводимый Windows-стенд (VM или физическая машина) с задокументированной процедурой. Второе нужно и само по себе: собранный установщик ни разу не запускался на Windows (docs/RELEASE.md), а первый же прогон release.yml в июле упал именно на Windows-специфичном коде.

**Детали, требования и минимальный набор** — `A2-backend.md`, раздел «Локальный Windows-путь»; эксперимент — V-001 в `verification-plan.md`.

## ADR-К3 — Разбор недоверенных документов: изоляция парсеров

**Проблема.** Продукт по назначению открывает файлы, приходящие извне (бухгалтерия — PDF и DOCX от контрагентов). Разбор идёт неподдерживаемой цепочкой крейтов (pdf-extract и его unic-*/ttf-parser — 6 предупреждений `unmaintained` в cargo audit): патчей безопасности для неё не будет.

**Что решать:** оставить как есть под наблюдением cargo audit; либо изолировать разбор (отдельный процесс/`catch_unwind` + таймаут + лимит памяти), чтобы враждебный файл не мог уронить или подвесить приложение; либо заменить парсер. Оценка последствий битого/враждебного PDF — `A6-security.md` (раздел «Поверхность атаки: разбор документов»).

## ADR-К4 — Разрыв циклической связности пятёрки модулей (гигиена, не дефект)

В проде связаны циклами `voice ↔ provision`, `diagnostics → voice → provision → diagnostics`, `memory → diagnostics → voice → provision → memory`. Зациклены **константы и две свободные функции**, состоянием модули не связаны, тестировать не мешают. Разрыв — два механических переноса: `hex_digest` в общие утилиты (снимает все три цикла) и константы модели распознавания в отдельный модуль данных. Делать не обязательно; решение — «делаем при следующем касании этих файлов» или «оставляем».
