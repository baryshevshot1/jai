## 2. Стратегия ошибок: error.rs + journal.rs (E0, оба файла целиком)

**Что сделано правильно (одной строкой, чтобы не сломали):** типизированные `AppError{code,message}` c пятью кодами и тестом сериализации; `From<String>` честно даёт `unknown`, не угадывая код по тексту; журнал = файл + stderr + хвост 200 записей для экрана «Диагностика», ротация 2 МБ на каждой записи (не при старте), бэклог до-файловых записей сбрасывается в файл, ошибки записи самого журнала глотаются осознанно и задокументированно; `journal::causes()` разворачивает цепочку `source()` с регрессионным тестом ровно на «error decoding response body».

**Систематическая слабость — урок C1-2 применён точечно (E1):**

- `journal::causes()` вызывается ровно **один раз** во всём бэкенде — download.rs:98. Путь загрузки голосовой модели — единственный, где цепочка причин доезжает до журнала.
- `AppError::from_reqwest` (11 мест: chat.rs:184,360; models.rs:109,178,231,337,395; memory.rs:202,225; embed.rs:57) различает timeout/connect по самой ошибке — это хорошо; но ветка «прочее» (error.rs:65) кладёт в message только верхний `Display` (`{e}`) — тот самый зонтик. Класс ошибок «тело оборвалось/не разобралось» на чат-пути снова даст «error decoding response body» без причины — в UI и в журнале.
- **Агентный путь хуже чатового:** agent.rs:127 вообще не использует from_reqwest — голый `format!("Не удалось подключиться к Ollama: {e}")` в String → код unknown; фронт в онлайн-чате не отличит «движок лежит» от прочего, хотя в обычном чате отличает. Несимметрия двух путей одного и того же вызова.
- `AppError` не хранит источник (нет поля/механизма для цепочки) — восстановить причину постфактум из журнала можно только там, где вызвавший сам позвал causes(). → Находка F-BACKEND-004 (P2).

Замечание к полноте кодов: `ErrorCode` не имеет варианта для «нет места на диске» — отказ записи истории/моделей уйдёт как unknown с текстом ОС (по-английски на англ. локали ОС). Вернусь в A2b (файловая система) с конкретными местами.

**Чего в матрице кода нет вовсе (найдено верификацией):**

1. **Штатный перезапуск при обновлении — вероятный регулярный источник сирот.** `settings.ts:623` вызывает `relaunch()` плагина process; проходит ли этот путь через `RunEvent::Exit` (а значит, гасится ли движок) — по коду не определить. Это не аварийный сценарий, а ежедневная кнопка. → V-014.
2. **«Внешний движок умер»** — сценария нет: монитор заводится только на своей ветке спауна, а `monitor_on` (`engine.rs:304`) нельзя перевзвести. Если движок при старте был внешним и потом умер — самовосстановления не будет никогда до перезапуска приложения.
3. **Гашение по переиспользованному PID.** `was_started_by_us` (`engine.rs:442-452`) пожинает труп через `try_wait`, но **не сбрасывает** `started_by_us` и не забирает `child`; затем `stop_if_ours` шлёт `libc::kill(-pid, SIGTERM)` по сырому pid (`engine.rs:484-486`) — если ОС успела выдать этот pid другому лидеру группы, сигнал уйдёт постороннему процессу. Вызывается из пяти мест (включая `provision.rs:766`, `settings.rs:160`).
4. **`reload_engine` не валидирует каталог моделей** (`settings.rs:172`) — фильтр `validate_models_dir` стоит только в `ensure_engine` (`settings.rs:133-147`). Кнопки «Применить каталог»/«Сбросить пути» поднимут движок с несуществующим `OLLAMA_MODELS` (флешку вынули) — модели «исчезнут» без предупреждения в журнале. Регрессия уже вылеченного бага.
5. **`resolve_exe` проверяет только `is_file()`** — любой файл с именем `ollama` в PATH будет запущен с `serve`, дальше тихий 30-секундный таймаут.

## 7. Async-дисциплина и гонки: главное — синхронные команды идут в потоке интерфейса

**Механика (E1, проверена по исходникам Tauri, не по документации).** `#[tauri::command]` над не-async функцией даёт `ExecutionContext::Blocking` (`tauri-macros-2.6.3/src/command/wrapper.rs:50,126-129,251`): тело выполняется прямо в обработчике IPC-протокола, который webview вызывает в своём потоке. Проект **знает** этот механизм и объясняет его в комментарии `documents.rs:36-38`, применив `#[tauri::command(async)]` к пяти командам документов. К остальным — нет.

**Счёт (E1, скрипт по 22 модулям, исключая тесты): 25 команд `async fn`, 5 с атрибутом `(async)` — и 24 чисто синхронные.** Среди последних — вся работа с историей, проектами, настройками и обход дисков:

| Команда | Что делает в потоке интерфейса | Когда вызывается |
|---|---|---|
| `save_conversation` (history.rs:124) | сериализация всего диалога + запись + **два fsync** (`write_atomic`) | на каждое сообщение, каждый ответ и автосейв раз в 5 с во время стрима (`chat.ts:619`) |
| `list_conversations` (history.rs:67) | обход каталога, чтение и разбор шапок всех диалогов | сразу после каждого сохранения (`conversations.ts:109`) |
| `find_model_sources` / `find_voice_model_source` (provision.rs:49,612) | перечисление **всех томов** + рекурсивный обход манифестов | мастер установки — первый экран у клиента |
| `delete_project` (projects.rs:115) | SQLite-каскад + чтение **всех** файлов диалогов целиком | удаление проекта |
| `get_setting`/`set_setting` (settings.rs:38,62) | чтение/перезапись settings.json | десятки раз при старте и на каждый тумблер |

Для Ирины это значит: в обычном чате — рывок после каждого ответа; в диалоге с картинками (base64 — мегабайты в JSON) окно перестаёт отвечать на секунды после каждого ответа; в мастере установки на Windows с подключённым, но недоступным сетевым диском окно висит до таймаута SMB (десятки секунд), потому что `sysinfo` перечисляет и такие тома. → **F-BACKEND-016 (P1)**.

**Гонки и блокировки (подтверждённые чтением обеих сторон):**

- **«Стоп» может не дойти до движка** (`chat.rs:407` против `lib.rs:57`): `cancel_stream` — синхронная и взводит флаг немедленно, а `chat_stream` — асинхронная, и её `cancel.begin()` создаёт **свежий** флаг позже, на воркере. Если все воркеры заняты, «Стоп» взведёт старый флаг, который новый запрос уже заменил: интерфейс остановится, а генерация в Ollama продолжится — греется GPU, память занята. → F-BACKEND-017 (P2).
- **Перезапуск движка из настроек убивает Ollama под идущим ответом**: `reload_engine` безусловно зовёт `stop_if_ours` (`settings.rs:161`), не проверяя, идёт ли генерация; ответ обрывается «Ответ движка оборвался» без указания причины. Плюс `stop_if_ours` блокирует воркер рантайма до 3 секунд (`engine.rs:487-492`) — в том же файле для той же операции в `ensure()` используется `spawn_blocking` (`engine.rs:265`).
- **Две параллельные индексации** ничем не сериализованы (в интерфейсе две независимые панели документов — сайдбар и экран проекта): конфликт всплывает сырой английской ошибкой SQLite после минут ожидания.
- **Журнал исходящих пишется блокирующе внутри агентного цикла** до 4 раз за вопрос, с read-modify-write без лока (`agent.rs:258,330`): «Очистить журнал» ровно между чтением и записью вернёт удалённые записи обратно.

**Что проверено и оказалось корректным** (не сломать при переделке): мьютексы через `.await` не держатся ни в одном из шести управляемых состояний; `MODEL.lock()` в whisper держится долго, но внутри `spawn_blocking`; фоновые задачи (idle-watch голоса, монитор движка, watchdog памяти) не размножаются; отмена стрима через `with_cancel` реально рвёт HTTP-соединение.

## 9. Механическая проверка правила (пункт 5): проверка возможна, но только узкая

Числа по проду (без тестовых модулей): `let _ =` — 69, `unwrap_or(...)` — 73, `unwrap_or_else` — 46, `if let Ok(` — 30, `.ok()` — 22, `Err(_) =>` — 19, `unwrap_or_default()` — 18. **Ни один паттерн нельзя запретить целиком** — законных мест кратно больше дефектных.

Что разделяет классы механически — проверено по признакам:

- **Тип операции — единственный надёжный признак.** Сужение `let _ =` до изменяющих файловых операций (`remove_file`/`rename`/`write`/`copy`/`write_atomic`) режет 69 → **17**, отсекая 75% шума одним фильтром.
- **Граница `#[cfg(test)]` обязательна:** без неё те же 17 превращаются в 61 (44 хвоста уборки временных каталогов в тестах).
- **Соседний `journal::` не работает как признак:** среди 17 файловых мест рядом нет ни одного вызова журнала — законные не логируют по определению («уборка»), дефектные не логируют потому, что это дефект.
- **Имя переменной — ловушка:** покрыло бы 10 из 15 законных, но пропустило бы ровно дефектные (`provision.rs:544`, `voice.rs:167`).

**Итог: проверка реалистична в виде «17 срабатываний, из них 3 дефекта, 14 размечаются маркером».** Три дефекта, которые она ловит сегодня, — ровно найденные аудитом P0/P1: `history.rs:153` (очистка истории), `projects.rs:155` (каскад удаления), `agent.rs:348` (журнал 152-ФЗ). Проектное решение и точный вид проверки — в `adr-candidates.md`, ADR-К1.

## 10. Разбор недоверенных документов (пункт 4) — передаётся в A6

Кратко: гигиена вокруг PDF **лучше среднего** — есть лимит входа 64 МБ до разбора и `catch_unwind` вокруг парсера (`documents.rs`), то есть ~120 точек паники в pdf-extract (49 `unwrap` на 2416 строк — плотность «одна на 20 строк») перехватываются. Но два вектора обходят `catch_unwind` **по конструкции**: (1) **переполнение стека** от неограниченной рекурсии по XObject — это `abort`, а не паника: окно исчезает без сообщения и без записи в журнал; (2) **deflate-бомба** — `read_to_end` без потолка, лимит входа 64 МБ при степени сжатия 1032:1 даёт до ~66 ГБ в памяти, отказ аллокации — снова `abort`. Плюс нет таймаута на разбор. Ветка DOCX (quick-xml, ~60 точек паники) `catch_unwind` **не обёрнута** вовсе. `zip` и `image` — в порядке (у image лимиты применяются). Полный разбор и вердикты — в A6-security.md; находка заведена сейчас (F-SECURITY-002).

## 11. Локальный Windows-путь (пункт 1) — отдельная находка P0

`release.yml` на windows-раннере не делает ничего Windows-специфичного: checkout → setup-node по `.nvmrc` → rust-toolchain 1.96.0 (хостовый MSVC-таргет) → rust-cache → `npm ci` → `tauri-action` с секретами подписи. Системные зависимости ставятся **только** для Ubuntu — на Windows всё берётся из образа раннера (MSVC, Windows SDK, NSIS/WiX, WebView2), и **в репозитории это нигде не задокументировано**. Артефакты определяются `"targets": "all"` → NSIS + MSI; на флешку кладётся только `*-setup.exe`.

`docs/RELEASE.md` отвечает на вопрос прямо и честно: *«Windows без Windows-машины или self-hosted runner не собрать никак»* (RELEASE.md:96-98), а раздел 3.1 называется «Windows не запускался ни разу»: локальная кросс-проверка `cargo xwin check` идёт с `--no-default-features`, то есть **модуль голоса под Windows не проверен даже компиляцией**; «Уровень 2 (собрать установщик и запустить на живой Windows) — стенда нет».

**Минимальный набор для воспроизведения** (собран по факту, в документах отсутствует): Windows 10/11 x64 (VM подойдёт), ~40 ГБ диска; Rust 1.96.0 с `x86_64-pc-windows-msvc`; Visual Studio Build Tools с рабочей нагрузкой «Desktop development with C++» (нужна и для MSVC-линковки, и для cmake-сборки whisper); Node по `.nvmrc`; cmake — **обязателен**, потому что релиз идёт с `default = ["voice"]`; NSIS/WiX подтягивает tauri-cli; переменные `TAURI_SIGNING_PRIVATE_KEY` и `..._PASSWORD` для updater-артефактов (ключ хранится вне репозитория, в секретах CI — **на новой машине его надо будет откуда-то взять**); для доверия ОС нужен EV-сертификат, без него SmartScreen встретит клиента предупреждением. Риск «собрать вслепую» подтверждён историей: первый же прогон release.yml упал именно на Windows-специфичном коде (PR #3, сигнатура GetDesc). → **F-PROVISIONING-003 (P0)**, эксперименты — блок Windows в плане верификации.

**P1:** F-BACKEND-016 (24 синхронные команды в потоке интерфейса), F-BACKEND-017 (осиротевший движок + ложная диагностика), F-BACKEND-018 (монитор движка: один спаун, ни журнала, ни события), F-BACKEND-019 (две копии: настройки и диалоги затираются).
**P2:** F-BACKEND-020 (потерянный «Стоп» и убийство движка под ответом), F-BACKEND-021 (reload_engine не валидирует каталог; kill по переиспользованному pid), F-BACKEND-022 (импорт без проверки места; индексация теряет минуты работы), F-BACKEND-023 (UAC, права каталога, кириллица+whisper — Windows-группа), F-BACKEND-024 (нет кода ошибки «нет места/прав»; tmp-мусор).
