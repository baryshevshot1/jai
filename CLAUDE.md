# CLAUDE.md — контекст проекта jai

> Этот файл Claude Code читает в начале каждой сессии. Он задаёт стек, правила и границы проекта.
> Держи его в корне репозитория и обновляй, когда меняются ключевые решения.

## Что это за проект

**jai** — боксовый офлайн ИИ-ассистент для российского бизнеса. Десктоп-приложение: клиент открывает по иконке, оно работает **полностью на его компьютере** (без облака, данные не покидают ПК — 152-ФЗ), без терминала. Бизнес-модель — установка под ключ.

## Стек (фактический)

- **Оболочка:** Tauri 2 (Rust) — окно, упаковка под Linux/Windows.
- **Фронтенд:** TypeScript + **Vite** (шаблон `vanilla-ts`). Dev-сервер на `http://localhost:1420`.
- **Бэкенд:** Rust (`src-tauri/`) — детект железа, менеджер моделей, контроль движка.
- **Движок нейросетей:** ТОЛЬКО **Ollama**, локальный HTTP API на `http://127.0.0.1:11434`.
- **RAG/эмбеддинги:** sqlite-vec (один файл БД) + модель bge-m3.
- Идентификатор приложения: `ru.baryshevshot.jai`.

## Жёсткие правила (не нарушать без явного запроса)

1. **Единственный движок — Ollama.** НЕ добавлять второй движок (llama.cpp и т.п.) без явного запроса. Речь (STT/TTS) — это Стадия 2, не сейчас.
2. **Сеть — по умолчанию только localhost.** В офлайн-ядро исходящие соединения с пользовательскими данными НЕ добавлять. Ollama слушает только `127.0.0.1`, никогда `0.0.0.0`. Единственное исключение — опциональный **агентный режим** (выход в интернет через tool-calling; сейчас — веб-поиск): выключен по умолчанию, включается пользователем явным тумблером. **Реализован** отдельным изолированным HTTPS-клиентом (`tools.rs` + команда `agentic_chat`), не смешанным с localhost-клиентом Ollama. См. раздел «Агентный режим / онлайн-слой».
3. **Персональные данные не покидают ПК.** Всё хранение и вычисления — локально.
4. **Офлайн после установки.** Приложение должно работать без интернета (модели уже скачаны). Проверки сети — неблокирующие.
5. **Никаких секретов в коде/гите.** Ключи подписи, токены, `.env` — мимо репозитория (см. `.gitignore`).

## Архитектура (целевая)

```
Tauri-окно (TypeScript + Vite: чат, проекты, документы, светофор железа, проверка системы)
        ↕ invoke / emit-listen
Rust-бэкенд (src-tauri):
  • Детектор железа     — RAM, CPU, видеокарта (Windows: DXGI), VRAM
  • Менеджер моделей     — качает из реестра Ollama и с Hugging Face, проверяет, ставит
  • Планировщик запуска  — plan_inference: снизить контекст / взять модель полегче / отказать
  • Контроль движка      — наличие/версия Ollama, порт, гасит СВОЮ группу процессов
        ↕ только http://127.0.0.1:11434
Ollama (один движок): текст, русский, код, зрение+OCR (qwen3-vl), эмбеддинги (bge-m3)
        ↕
Данные на ПК пользователя: история, индекс sqlite-vec, модели — ничего не уходит наружу
```

## Целевое железо (тест)

MacBook (разработка) · Linux-ПК с NVIDIA 6 ГБ VRAM / 64 ГБ RAM (тест собранного продукта). Модель 8–9B (Q4_K_M) на 6 ГБ — впритык, держать контекст ≤ 8k.

## Кроссплатформенность (важно при написании кода)

Продукт собирается под **Linux и Windows** (и macOS на будущее), хотя разрабатывается на Mac. Поэтому весь код должен быть портируемым:

- **Пути — только через Tauri path API** (`appDataDir`, `appConfigDir`, `appLogDir` и т.п.). Никогда не хардкодить разделители (`/` или `\`) и абсолютные пути.
- **ОС-специфичный код Rust — через `#[cfg(target_os = "...")]`** (`windows` / `linux` / `macos`). Не предполагать одну ОС.
- **Детект видеокарты/VRAM — отдельные ветки:** Windows — DXGI (крейт `windows`); Linux — `nvidia-smi` / `rocm-smi`; macOS — Metal/unified memory. Не использовать WMI `AdapterRAM` (режет до 4 ГБ).
- **Управление процессом движка** (запуск/остановка Ollama, освобождение порта) — учитывать различия Windows и Unix; гасить свою группу процессов кроссплатформенно.
- **Windows-установщик — офлайн:** `webviewInstallMode: offlineInstaller` уже задан в `tauri.conf.json` (WebView2 ставится без интернета). На Linux это не требуется (системный webkit2gtk).
- **Сборка установщиков — только в CI** (`.github/workflows/release.yml`, matrix из 3 ОС). Tauri не кросс-компилит — с Mac собрать Windows/Linux напрямую нельзя.
- Не завязываться на команды/утилиты, специфичные для одной ОС, без `#[cfg]`-ветки и проверки наличия.

## Принятые решения (ADR)

Короткие записи «что решили и почему». Пересматривать — только явным решением: за
каждой стоит либо проверка, либо отказ, который уже случился.

### 1. Голосовой ввод — cargo-фича `voice`, включённая по умолчанию

`default = ["voice"]`. Сборка `--no-default-features` обязана собираться и работать
без cmake и C++-тулчейна: команды голоса при этом зарегистрированы, но отвечают
честным отказом, а интерфейс не показывает кнопку микрофона.

**Почему фича, а не «всегда»:** whisper.cpp компилируется из исходников (минуты и
внешний тулчейн), и быстрая проверка логики не должна за это платить. **Почему
команды регистрируются всегда:** иначе `invoke` реджектится, исключение обрывает
цепочку старта, и «нет голоса» становится неотличимо от «приложение сломалось».

Матрица фич входит в полный ярус гейта — она уже поймала отказ сборки без голоса.

### 2. Локальный гейт вместо CI

GitHub Actions недоступны (аккаунт заблокирован по оплате). Источник правды —
`tools/check.sh`; workflow-файлы переведены на `workflow_dispatch` и продолжают
документировать, что должно проверяться. Ярусы, хуки, зелёный штамп и релизный
контур — в [`docs/RELEASE.md`](./docs/RELEASE.md).

Ключевое: `tools/release.sh` **отказывается** собирать бандл без зелёного штампа
полного яруса, совпадающего с HEAD, на чистом дереве. Это заменяет branch protection.
Пропущенная проверка (нет Docker, нет llvm-rc) штамп тоже отменяет: «проверено кроме
Windows» и «проверено» — разные вещи.

### 3. Изоляция инициализации

`main.ts` — реестр модулей, каждый в своём `try/catch` (`src/boot.ts`). Отказ одного
не отменяет остальные, но **проглоченных исключений нет**: отказ уходит в журнал и на
видимую плашку. Интерфейс, целый за счёт съеденной ошибки, — худший исход: чинить его
начнут не раньше, чем он развалится у клиента.

### 4. Контракт команд — список как данные

`COMMAND_NAMES` в `lib.rs` живёт рядом с `generate_handler!`, тест
`command_contract::declared_names_match_generate_handler` не даёт им разойтись.
Список видно во время работы — на экране «Проверка системы» и в `jai --self-check`.
Прежняя проверка (`tools/check-dom.py`) разбирала исходник и отвечала на вопрос «что
написано»; вопрос стоял «что попало в бинарник».

### 5. Доставка модели распознавания клиенту — флешка

**Решение владельца: флешка основная, интернет запасной.** У клиента интернета нет;
полагаться на скачивание 465 МБ при установке нельзя. Модель кладётся на носитель
через `tools/make-usb.sh --voice`, оба пути установки ведут в один файл и оба
заканчиваются сверкой sha256.

Скачивание из интернета остаётся — им пользуется владелец продукта и клиенты, у
которых сеть есть. Оно переделано: докачка по `Range`, повторы, атомарная публикация,
человеческие ошибки. Ссылка, размер и сумма заданы в `voice.rs` и `tools/make-usb.sh`;
их совпадение проверяет тест.

### 6. Большие загрузки — отдельный HTTP-клиент

`tools::download_client()` **не имеет общего таймаута на запрос**, только
`connect_timeout` и `read_timeout`. Причина записана кровью: общий `.timeout(20 c)` у
клиента онлайн-слоя покрывает в reqwest и чтение тела, из-за чего загрузка модели
обрывалась ВСЕГДА и у ВСЕХ — с текстом «error decoding response body», в котором про
таймаут нет ни слова. Медленную загрузку от мёртвой отличает **молчание потока**, а не
её общая длительность. Регрессионный тест — `download::tests::no_total_timeout_on_the_download_path`.

### 7. Журнал приложения вместо просьбы открыть консоль

`src-tauri/src/journal.rs`: файл + stdout + хвост в памяти для экрана «Диагностика»,
плюс `journal::causes()` — разворачивание цепочки `source()`. Своё, а не
`tauri-plugin-log`: экрану нужен хвост в памяти, которого плагин не даёт, а лишняя
зависимость в офлайновом коробочном продукте — лишний риск сборки.

## Агентный режим (Стадия 2, опционально)

Опциональная надстройка над офлайн-ядром: даёт модели выход в интернет через
tool-calling (веб-поиск, чтение URL, готовые API — погода, курсы валют, новости).
Это дополнение, а не замена офлайн-ядра.

- **Выключен по умолчанию.** Базовый продукт остаётся полностью офлайновым; в офлайн-ядро сетевые вызовы не добавлять.
- **Включается явным тумблером пользователя** — не молча и не «по умолчанию потом».
- **Прозрачность в интерфейсе:** видно, когда был использован интернет (какой инструмент, какой запрос/URL).
- **Контролируемые инструменты, а не «модель гуляет по сети».** На каждый инструмент — отдельная Rust-команда с чёткой зоной ответственности; список инструментов фиксирован, модель не открывает произвольные соединения.
- **Корректный tool-calling:** модель должна возвращать `tool_calls` (нужен правильный chat-template модели); разбор текста «на глазок» — не путь.
- **152-ФЗ:** данные, уходящие наружу при работе инструмента, покидают ПК **только с явного согласия пользователя** (включённый тумблер) и в минимально необходимом объёме; что именно ушло — видно в интерфейсе. Персональные данные офлайн-ядра наружу по-прежнему не уходят.
- **Очерёдность:** реализуется ПОСЛЕ готовности офлайн-ядра (MVP), не раньше.
